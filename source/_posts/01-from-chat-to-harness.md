最近开始接触 AI Agent Harness。这里的 Harness 指围绕 LLM 提供工具、上下文、权限控制和执行循环的运行框架。最初的印象很简单：它大概就是一个比普通 Chat 更强的聊天工具，能读取项目文件，也能执行终端命令。

这个理解虽然粗糙，但很适合作为起点，并且可以随着后续概念逐步扩展。

<!-- more -->

## 从普通 Chat 开始

普通 Chat 最容易理解。

例如提出一个 Java 问题：

> Maven 编译时提示某个 Maven 依赖无法解析，应该怎么处理？

模型可以根据使用者提供的信息分析问题，告诉使用者可能需要检查 Maven 远程仓库、本地仓库或者依赖项目。

但它有一个明显限制：真正的操作还是需要使用者自己完成。

使用者需要自己打开 `pom.xml`，自己执行：

``` bash
mvn compile
```

然后把错误复制给模型。模型分析后，如果认为需要编译某个本地依赖，使用者再去寻找对应项目并执行：

``` bash
mvn install
```

整个流程实际上是：

``` text
使用者操作环境
    ↓
把结果告诉 LLM
    ↓
LLM 给建议
    ↓
使用者继续操作
```

LLM 更像一个坐在旁边提供建议的人。这里所说的普通 Chat，指不具备文件、终端等外部工具调用能力的纯对话模式。

## Harness 带来的第一层变化

到了 Harness 场景，LLM 不再只能等使用者复制信息。

如果 Harness 提供了文件和终端等 Tool，它可以自己：

``` text
读取 pom.xml
    ↓
执行 mvn compile
    ↓
读取编译错误
    ↓
判断缺少本地依赖
    ↓
搜索工作目录
    ↓
找到依赖项目
    ↓
执行 mvn install
    ↓
重新编译
```

这里最明显的变化就是：LLM 获得了操作外部环境的能力。

因此，在当前阶段，可以把 Harness 暂时理解为：

> LLM + Tools。

虽然这个定义后面还会不断扩展，但它足够解释为什么 Harness 和普通 Chat 的使用体验有明显差异。

## Tool 是什么

Tool 可以暂时理解成 LLM 可调用的外部能力。

例如 Coding Agent 常见的 Tool 包括：

``` text
读取文件
修改文件
搜索文件
执行 Shell
Git 操作
访问浏览器
调用外部服务
```

LLM 本身并不会真的执行 `mvn compile`。

它只是判断：

> 现在应该执行 Maven 编译。

然后通过 Harness 提供的 Shell Tool 发起操作，真实环境执行命令后，再把结果返回给模型。

因此可以把过程拆成：

``` text
LLM
 ↓
决定下一步动作
 ↓
Tool
 ↓
真实环境
 ↓
执行结果
 ↓
LLM
```

这个区别很重要。

LLM 负责理解和判断，Tool 负责真正做事。

## 一个更真实的 Maven 场景

假设某个 Spring Boot 项目的 Maven 依赖无法正常解析。

普通 Chat 中，通常需要多轮操作：

1.  执行编译；
2.  复制错误；
3.  询问模型；
4.  检查依赖配置；
5.  修正依赖问题；
6.  重新编译；
7.  把新错误继续发给模型。

而拥有 Tool 的 Agent 可以自己完成其中的大部分步骤。

例如第一次 Maven 返回：

``` text
Could not find artifact example:dependency
```

假设模型分析后认为这可能是未安装的本地项目依赖，于是搜索当前 Workspace。

如果发现：

``` text
../示例依赖/pom.xml
```

它就可能继续进入该项目执行 `mvn install`，再回到原项目重新编译。为了先说明工具调用过程，这里暂时忽略权限审批；相关问题会在下一节讨论。

这里已经出现了一个非常重要的模式：

``` text
观察
→ 判断
→ 操作
→ 获得新结果
→ 再判断
```

后面会把它称为 Agent Loop。

## Tool 不代表无限权限

还有一个很容易产生的误解：

> LLM 有 Shell Tool，是不是等于它可以随便操作机器？

并不是。

Tool 能做什么、Harness 是否允许执行、某些操作是否需要人工确认，是另外一层问题。

例如，某个 Harness 的权限策略可以设计成：

``` text
读取文件       自动允许
修改项目文件   自动允许
mvn test       自动允许
git commit     需要确认
git push       需要确认
危险删除操作   禁止
```

因此 Tool 表示的是"能力"，而不是"无限授权"。

这也是 Harness 相比单纯把一个 Shell 交给模型更重要的地方。

## 第一阶段的心智模型

到这里暂时不需要引入 Skill、MCP、RAG 等更多概念。

第一阶段只需要记住：

``` text
普通 Chat
=
LLM 给建议
人负责操作

Harness / Coding Agent
=
LLM
+
Tool
+
真实环境
```

于是 LLM 从一个只能回答问题的模型，开始变成一个可以在真实项目里持续工作的 Agent。

但新的问题也随之出现。

一个 Spring Boot 项目可能有几千个文件。LLM 怎么知道应该读取哪些？项目里存在某个文件，是否意味着模型已经知道它的内容？项目开发规范应该每次都重新告诉它吗？

这些问题会引出下一篇的概念：**Context 与 Instruction**。

## 小结

目前可以形成这样的基础认识：

-   LLM 负责理解、推理和决定下一步；
-   Tool 提供文件、终端、Git 等外部操作能力；
-   Harness 让 LLM 能够调用这些能力；
-   Tool 执行结果重新返回给 LLM，形成继续工作的基础；
-   有 Tool 不等于拥有无限权限。

这是从普通 Chat 进入 Harness 时建立的第一层认知。后面的所有概念，基本都可以从这个简单模型继续往外扩展。
